Story Retrieval Chatbot · data pipeline

From the dataset to the Qdrant index

Two commands turn the 1,000 stories into everything the agent searches. prepare_data.py loads, cleans and splits the stories. build_index.py chunks them, embeds every chunk three ways, and stores the results in two Qdrant collections on disk.

The whole flow

Everything is written inside the project folder. Qdrant's database lives in qdrant_data/ (set by qdrant.path in configs/retrieval.yaml).

Each step

1

Load the stories

data/load.py · load_stories()
  • Reads data/stories.parquet if it exists. A .csv, .json or .jsonl copy also works.
  • Otherwise downloads FareedKhan/1k_stories_100_genre from the Hugging Face Hub. This happens only on the first run.
in: dataset (1,000 stories)out: DataFrame id, title, genre, story
2

Clean

data/load.py · _clean()
  • Keeps the four columns id, title, genre, story and fails if one is missing.
  • Turns ids into integers, so they can be used directly as Qdrant point ids. Duplicate ids stop the build with an error.
  • Makes duplicate titles unique. Titles are compared after normalisation (lowercase, no punctuation, single spaces). The first story keeps its title; later ones become Title - Vol 2, Title - Vol 3, and so on.

Unique titles mean a title lookup always lands on exactly one story.

3

Save the title/genre metadata and a local copy

data/load.py · save_story_metadata() · data/prepare.py
  • story_metadata.json maps each normalised title to its id, original title and genre, and lists the unique genres. The agent's fuzzy title and genre matching reads this file.
  • stories.parquet is a local copy of the cleaned stories, so later runs never need the Hub.
{"title_map": {"the great oceanic quake": {"id": 183359, "title": "The Great Oceanic Quake", "genre": "Disaster"}, ...},
 "genres": ["Alternate Reality", "Animal Fiction", ...]}
data/story_metadata.jsondata/stories.parquet
4

Split train / validation / test

data/splits.py · make_split()
  • Splits within each genre: 20% test and 10% validation (at least one story each), and the rest for training. Seed 42.
  • The split is saved once and then frozen: later runs load it instead of making a new one. Task 2 (genre classifier) uses the same file, so both tasks agree on which stories are held out.
  • The index holds all stories; the split column is only for evaluation and Task 2.
data/splits.json
5

Chunk

retrieval/chunking.py · build_chunks()
  • A story of up to 1,000 tokens stays one chunk.
  • A longer story is split into sentence-aligned chunks of about 400 tokens. Each chunk starts a few sentences back, so neighbouring chunks share about 50 tokens.
  • Chunks are stored as character spans (start, end) into the original story, so the chunk text is always an exact substring. Late chunking (step 6) relies on this.
  • Every chunk gets a header line with its story's title and genre: Title: The Great Oceanic Quake | Genre: Disaster.

Sentence boundaries keep answer sentences intact; the header lets a chunk match a title or genre even when its text never mentions them.

6

Embed each chunk three ways

retrieval/embed.py · retrieval/indexing.py

dense_late

Late chunking, the vector the agent searches with. search_document: + header + the whole story go through nomic-ai/modernbert-embed-base in one pass (up to 8,192 tokens). The token vectors are then averaged per chunk: a token belongs to a chunk when the middle of its characters falls inside the chunk's span. So each chunk vector carries context from the whole story.

dense_prefix

The baseline for comparison: each chunk embedded on its own with the same prefix and header, up to 1,100 tokens so whole-story chunks are not cut at 512.

sparse (BM25)

Keyword vectors from FastEmbed Qdrant/bm25 on header + chunk text, without the search_document: prefix. Qdrant applies the IDF weighting. This catches exact names and rare words.

All vectors are L2-normalised and compared with cosine. Runs on a GPU when there is one (fp16), otherwise on the CPU.

8

Write the manifest

retrieval/indexing.py · build_index()
  • The manifest is written last, after every upload finished. It records the model, chunk settings, story and chunk counts, and how long each step took.
  • Before uploading, any old manifest is deleted, so an interrupted build never looks finished.
  • Running the build again skips all the work when the manifest exists and its counts match Qdrant. --rebuild forces a fresh build.
qdrant_data/build_manifest.json

How the agent uses what was built

Title or genre typed by the user

Fuzzy-matched against story_metadata.json; the original title or genre then becomes a Qdrant filter.

Story by id or title

Read straight from the stories collection, no vectors involved.

Search

The query is embedded with search_query: and as BM25; the two result lists from story_chunks are fused with RRF and grouped by story.

Question about one story

The same hybrid search, filtered to a single story_id.
